# Интеграция с CS2 через Game State Integration

Дата: 2026-09-06

Подсветка HyperHDR реагирует на игровые события CS2: смерть — два красных
мигания, заложенная бомба — оранжевый пульс с ускорением, флешка — белый.

## Почему GSI и почему это безопасно

Game State Integration — штатный механизм Valve. В каталог
`.../Counter-Strike Global Offensive/game/csgo/cfg/` кладётся файл
`gamestate_integration_<имя>.cfg`, и игра **сама** шлёт HTTP POST с состоянием
на указанный адрес. Мы не читаем память, не внедряем код, не открываем
дескрипторы процесса игры — процесс CS2 не трогается вообще. На этом же
механизме работают стрим-оверлеи и табло HLTV. Повода для реакции VAC нет.

В обычном матче GSI отдаёт только данные самого игрока; данные остальных
доступны лишь наблюдателю и GOTV. Преимущества в игре механизм не даёт.

Отсюда следует ограничение на весь проект: **никаких обращений к процессу
`cs2.exe`**. Определение «игра запущена» делается только перечислением
процессов (`Toolhelp32Snapshot`), без `OpenProcess`. Точное время старта
процесса дало бы более точную подсказку в UI, но обращение к дескриптору
чужого игрового процесса — ровно то поведение, которое выглядит как чит,
и ради удобства подсказки эту гарантию ломать нельзя.

## Ключевой факт о протоколе

Игра **не шлёт события**. Она с заданной периодичностью отправляет полный
снимок состояния плюс блок `previously` со старыми значениями изменившихся
полей. «Смерти» в потоке нет — есть `player.state.health: 0` рядом с
`previously.player.state.health: 34`. Все события мы выводим сами, сравнивая
кадры.

## Что показала запись

Дамп снят (`internal/cs2/testdata/session-casual.jsonl`, 65 кадров, casual
de_dust2, steamid и ник заменены фиктивными). Итоги:

- **Блоки `bomb` и `phase_countdowns` не приходят ни разу.** Таймер до взрыва
  игроку недоступен, как и в CS:GO. Запасной путь становится единственным:
  отсчёт мост ведёт сам от появления `round.bomb = "planted"`.
- `round.bomb` принимает только значение `planted`; конец жизни бомбы виден не
  значением, а исчезновением самого ключа.
- Смерть в записи произошла при `round.phase = "over"` (добило после конца
  раунда) и `map.phase = "live"`. Это подтверждает выбор гейта: по `round.phase`
  событие было бы потеряно.
- Подтверждённые поля `player.state`: `health, armor, helmet, flashed, smoked,
  burning, money, round_kills, round_killhs, equip_value` (+`defusekit` у CT).
- `map.phase`: `warmup|live`. `round.phase`: `freezetime|live|over`.
- `player.activity`: `menu|playing`.
- `flashed` во всех 50 игровых кадрах равен 0 — флешку поймать не удалось.
  Порог остаётся непроверенным, поэтому правило `cs2_flashed` поставляется
  **выключенным**.

**Игра шлёт кадр только при изменении состояния** (плюс heartbeat раз в 10 с):
65 кадров за шесть минут. Отсюда требование, которого не было в исходном
дизайне: фазы бомбы нельзя двигать из `Detector.Feed` — он вызывается только на
входящем кадре, а тикающая бомба состояние не меняет. Нужен собственный тикер
(`cs2.Tracker.Run`, шаг 200 мс), который вызывает `Detector.Tick`. Детектор при
этом остаётся чистым.

## Архитектура

Выбран путь расширения существующего конвейера, а не построения слоёв-
композитора: приоритет «CS2 важнее Discord» уже обеспечен тем, что
`rules.Match` берёт первое совпавшее состояние из `rules.order`. Достаточно
поставить `cs2_*` в начало списка.

```
CS2 ──HTTP POST──► cs2.Server ──► cs2.Detector ──┐
                                                 ├──► state.Store ──► rules.Engine ──► HyperHDR
Discord ──IPC──► discord.Client ──► ApplyEvent ──┘
```

### Пакет internal/cs2

| Файл | Ответственность |
|---|---|
| `payload.go` | типы GSI, больше ничего |
| `detect.go` | `Detector.Feed(Payload) Signals` — вся логика, без HTTP и горутин |
| `server.go` | HTTP-слушатель, проверка токена, сторож простоя |
| `install*.go` | поиск Steam, парсер VDF, запись cfg, `Status` |
| `process*.go` | `Running() bool` — только перечисление процессов |

Граница: **Detector квантует всё непрерывное сам** и отдаёт наружу только
дискретные признаки. Это не косметика. `state.Store` сравнивает снимки через
`s.cur == prev`; сырой `countdown` менял бы снимок каждые 100 мс, дедупликация
по `actionKey` перестала бы работать, и лента захлебнулась бы командами.

### Новые поля state.Snapshot

Все скалярные — структура остаётся сравнимой:

```go
CS2Live      bool // игра шлёт данные, матч идёт
CS2Dead      bool // одноразовый признак, гаснет по таймеру
CS2Flashed   bool // flashed выше порога
CS2BombPhase int  // 0 нет, 1 тикает, 2 спешить, 3 паника
```

Соответствующие `state.Kind`: `cs2_dead`, `cs2_flashed`, `cs2_bomb`,
`cs2_bomb_hurry`, `cs2_bomb_panic`.

## Правила детекции

**Смерть** — переход здоровья `>0 → 0` на своём игроке. Проверка
`player.steamid == provider.steamid` обязательна: после смерти игрок уходит в
наблюдатели и блок `player` начинает описывать тиммейта. При несовпадении
steamid история здоровья не обновляется вовсе, иначе чужой респавн прочитается
как своя жизнь, а чужая смерть — как своя.

Смерть засчитывается только при `map.phase == "live"` (флаг `only_when_live`,
по умолчанию включён) — иначе разминка с респавнами даёт непрерывное мигание.

**Смерть гаснет по таймеру**, а не держится до респавна. `CS2Dead` живёт
`death_hold_ms` и сбрасывается источником. Причина: `cs2_dead` стоит выше в
`order`, и липкий признак означал бы, что, умерев при заложенной бомбе, игрок
отмигает красным и следующие 40 секунд смотрит на погашенную ленту. С таймером
управление возвращается тикающей бомбе.

Отсюда требование валидации: `death_hold_ms` не меньше длительности анимации
(`blink_count × (blink_on_ms + blink_off_ms)`), иначе смена состояния оборвёт
мигание на середине.

**Флешка** — порог по `flashed` (`flash_threshold`, по умолчанию 100), признак
булев. Градации не делаются: HyperHDR и так льёт белый с захвата экрана,
разница между 180 и 220 на ленте не читается.

**Бомба** — отсчёт ведётся самостоятельно от момента `round.bomb == "planted"`:
записью подтверждено, что таймера в данных игрока нет. Длительность задаётся
`bomb_fuse_s` (по умолчанию 40 с) — это единственное число, которое обязано быть
верным, поэтому оно вынесено в конфиг. Конец — исчезновение ключа `round.bomb`.

Ускорение — три дискретные фазы, а не плавная кривая:

| Осталось | Состояние | Период по умолчанию |
|---|---|---|
| > `bomb_hurry_s` (20 с) | `cs2_bomb` | ~1000 мс |
| `bomb_hurry_s`…`bomb_panic_s` | `cs2_bomb_hurry` | ~500 мс |
| < `bomb_panic_s` (5 с) | `cs2_bomb_panic` | ~180 мс |

Три отдельных состояния вместо одного с параметром — чтобы движок правил
остался неосведомлённым о CS2: он по-прежнему берёт первое совпавшее имя из
`order`. Смена фазы меняет ключ действия, движок сам перезапускает цикл с
новым периодом.

**Игра закрылась.** GSI просто перестаёт слать данные. Без сторожа лента
залипнет оранжевой навсегда: нет POST дольше `idle_timeout_s` (30 с, при
`heartbeat 10.0` это три пропуска) — все `CS2*` в ноль.

## Конфигурация

```yaml
cs2:
  enabled: true
  addr: 127.0.0.1:7799
  token: ""              # генерируется при установке cfg
  cfg_path: ""           # пусто = искать Steam автоматически
  idle_timeout_s: 30
  only_when_live: true
  death_hold_ms: 1200
  flash_threshold: 100
  bomb_hurry_s: 20
  bomb_panic_s: 5

rules:
  order: [cs2_dead, cs2_flashed, cs2_bomb_panic, cs2_bomb_hurry, cs2_bomb,
          deafened, muted, connected]
  states:
    cs2_dead:       { type: color, color: [255,0,0],     blink_count: 2, hold: false }
    cs2_flashed:    { type: color, color: [255,255,255] }
    cs2_bomb:       { type: color, color: [255,90,0], loop: true, blink_on_ms: 500, blink_off_ms: 500 }
    cs2_bomb_hurry: { type: color, color: [255,90,0], loop: true, blink_on_ms: 250, blink_off_ms: 250 }
    cs2_bomb_panic: { type: color, color: [255,90,0], loop: true, blink_on_ms: 90,  blink_off_ms: 90 }
```

## Изменения в существующем коде

1. `state.Snapshot` — четыре поля и пять веток в `Has()` (фазы бомбы — отдельные
   состояния).
2. `config.Action` — поля `Loop bool` и `Enabled *bool`; в `rules.blink()` при
   `Loop` цикл крутится до отмены контекста (отмена уже реализована через
   `stopBlink()`), `Loop` добавлен в `actionKey()`.
3. `rules.Match` пропускает выключенные правила и уступает ход следующему в
   `Order` — выключатель должен отказываться от события, а не гасить ленту.
4. `app.App` — поля `CS2 *cs2.Server`, `CS2Track *cs2.Tracker` и две горутины
   в `Run()`.
5. `config.Load` — миграция `ensureCS2Rules`: в YAML список заменяется целиком,
   поэтому `rules.order` из старого конфига вытеснил бы события CS2, и они
   молча перестали бы срабатывать.

## Выключение событий

`Action.Enabled *bool`, где nil означает «включено» — иначе конфиги без этого
поля перестали бы работать после обновления. Выключение сделано флагом, а не
удалением имени из `Order`, чтобы приоритет сохранялся между включениями.

Флаг общий для всех событий, поэтому выключать можно и состояния Discord.
Панель показывает список событий с описанием, цветом, отметкой «сейчас» и
переключателем; сохранение идёт через существующую ручку `PUT /api/rules`.

## Установка cfg

`HKCU\Software\Valve\Steam` → `SteamPath`, оттуда `steamapps/libraryfolders.vdf`;
ищется библиотека, где в `apps` есть ключ `730`; путь складывается как
`.../common/Counter-Strike Global Offensive/game/csgo/cfg/`. Минимальный парсер
VDF пишется сам — тянуть зависимость ради одного файла не стоит, четыре прямые
зависимости проекта являются его достоинством.

Токен — 16 байт из `crypto/rand`, попадает и в `config.yaml`, и в cfg;
проверяется в HTTP-обработчике, чтобы посторонний локальный процесс не мог
подделать «ты умер».

`Status` по образцу `autostart.Status`: `Supported / Installed / Path / Stale /
Error`, где `Stale` — файл есть, но `uri` или токен разошлись с конфигом.
Ошибки прячутся в поле `Error`: панели нужен ответ, а не 500.

**cfg читается игрой только при старте.** После установки CS2 требуется
перезапустить, и панель обязана это прямо написать.

## Интерфейс

Блок «Интеграции» первым, до состояния и настроек: плитки Discord и CS2 —
статусная точка, название, строка-итог. Клик разворачивает детали под рядом
плиток; открыта всегда одна. Стиль существующей панели сохраняется: ванильный
JS, без сборки, без фреймворка.

Детали CS2: путь к игре, состояние конфига (`не установлен` / `установлен` /
`устарел — порт или токен изменились` / `Steam не найден`), адрес слушателя и
факт получения данных, кнопка «Установить конфиг» (при `stale` — «Обновить
конфиг»). При `Steam не найден` вместо кнопки — подсказка вписать `cs2.cfg_path`
руками.

Предупреждение о перезапуске игры показывается, когда игра запущена и при этом
конфиг отсутствует, устарел или был записан в этой сессии без последующего
перезапуска игры. Без времени старта процесса (см. ограничение выше) факт
перезапуска выводится состоянием: запоминается момент записи cfg, и если после
него игра хоть раз наблюдалась незапущенной, перезапуск считается состоявшимся.

Перечисление процессов не вешается на `/api/status`. Ручка `/api/cs2`
(GET — статус, POST — установить конфиг) опрашивается при открытии плитки, по
кнопке и раз в 3 секунды, пока плитка раскрыта.

Плитка Discord переносит в себя то, что уже отдаёт `/api/status`. Существующие
карточки состояния и переключатель автозапуска остаются на месте.

## Обработка ошибок

Принцип: **CS2 не должен ронять мост.** Discord-часть работает сегодня и не
должна страдать от того, что игра не установлена или порт занят.

| Что | Поведение |
|---|---|
| Порт занят | Лог и `Status.Error`, мост живёт на Discord |
| Steam не найден | `Status.Error`, панель предлагает вписать `cfg_path` |
| POST без токена | 403, предупреждение в лог не чаще раза в минуту |
| Битый JSON | 400, `debug` в лог, кадр отбрасывается |
| Игра закрылась | Сторож простоя обнуляет `CS2*` |

## Тестирование

Основная масса тестов — на `Detector`: он чистая функция, и в нём вся логика.

- `detect_test.go` на записанном дампе: ровно N срабатываний смерти за сессию,
  ни одного лишнего при переходе в наблюдатели, флешка поднимается и гаснет,
  фазы бомбы идут 1 → 2 → 3 и сбрасываются на взрыве
- `install_test.go` — парсер `libraryfolders.vdf` на фикстуре, рендер cfg
  golden-файлом
- `server_test.go` — `httptest`: верный токен, неверный, битый JSON, сторож простоя
- `rules` — `Loop` в существующем `blink_test.go`

## Этапы

**Этап 1** (пишется сразу, от структуры полей не зависит): секция конфига,
HTTP-слушатель, установщик cfg, определение запущенной игры, ручка `/api/cs2`,
плитки в панели, `cmd/gsiprobe` — диагностическая утилита по образцу
существующего `cmd/rpcprobe`, печатающая и пишущая в файл сырой поток GSI.

**Пауза:** установка cfg кнопкой, перезапуск CS2, игра оффлайн с ботами —
смерть, флешка, заложенная и взорванная бомба. Результат — `testdata/session.jsonl`.

**Этап 2** (по фактам из дампа): `payload.go`, `Detector`, поля в `Snapshot`,
`Loop` в движке правил, правила по умолчанию, `docs/cs2-integration.md` по
образцу `docs/discord-integration.md`, README.
